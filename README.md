# go-courier-shifts

[![CI](https://github.com/Mashna33/go-courier-shifts/actions/workflows/ci.yml/badge.svg)](https://github.com/Mashna33/go-courier-shifts/actions/workflows/ci.yml)

Учебный backend-сервис на Go для управления сменами курьеров: слоты по зонам доставки, запись на смену, старт и завершение смены, расчёт заработка. Сделан по мотивам задач курьерских сервисов доставки.

Главная техническая тема проекта — **корректность при конкурентных запросах**: что произойдёт, если два десятка курьеров одновременно записываются на последние места, и как гарантировать, что мест не окажется больше, чем есть.

**Стек:** Go 1.24 (стандартный `net/http`), PostgreSQL 16, Docker / Docker Compose, GitHub Actions.

## Быстрый старт

Нужны Docker и Docker Compose.

```bash
docker compose up --build        # сервис на http://localhost:8080, PostgreSQL на порту 5433
scripts/smoke.sh                 # сквозная проверка: проходит всю жизнь смены через HTTP
```

Пример сценария:

```bash
# курьер и слот на 4 часа (время в формате RFC 3339, ставка в копейках за час)
curl -X POST localhost:8080/couriers -d '{"name":"Анна"}'
curl -X POST localhost:8080/slots -d '{"zone":"center","starts_at":"2030-01-01T10:00:00Z","ends_at":"2030-01-01T14:00:00Z","capacity":2,"hourly_rate_kopecks":30000}'

curl "localhost:8080/slots?zone=center&limit=10"                  # слоты и число свободных мест
curl -X POST localhost:8080/slots/1/bookings -d '{"courier_id":1}' # записаться на слот
curl -X POST localhost:8080/bookings/1/start                       # начать смену
curl -X POST localhost:8080/bookings/1/finish                      # завершить: вернёт earned_kopecks
```

## API

| Метод и путь | Что делает | Основные ошибки |
|---|---|---|
| `POST /couriers` | создать курьера | 400 |
| `GET /couriers/{id}/bookings` | история смен курьера | 404 |
| `POST /slots` | создать слот (зона, начало, конец, вместимость, ставка) | 400 |
| `GET /slots?zone=&from=&to=&limit=` | список слотов с числом занятых и свободных мест | 400 |
| `POST /slots/{id}/bookings` | записать курьера на слот (`{"courier_id": 1}`) | 404, 409 `slot_full`, `slot_closed`, `shift_overlap` |
| `POST /bookings/{id}/cancel` | отменить запись до начала слота | 409 `cancel_too_late`, `invalid_state` |
| `POST /bookings/{id}/start` | начать смену (за 15 минут до слота и до его конца) | 409 `outside_start_window`, `invalid_state` |
| `POST /bookings/{id}/finish` | завершить смену и посчитать заработок | 409 `invalid_state` |
| `GET /healthz`, `GET /readyz` | живость сервиса и доступность базы | 503 |

Ошибки всегда приходят в одном формате: `{"error": "...", "code": "slot_full"}`. Для неожиданных ошибок клиент получает общее сообщение, подробности попадают только в лог.

## Правила

- Запись живёт по схеме `booked → started → finished` или `booked → cancelled`.
- Заработок считается в целых копейках и целых секундах (без `float`) и только за время **внутри слота**: если курьер начал раньше или закончил позже, лишнее не оплачивается.
- Курьер не может быть записан на две пересекающиеся смены. Смена, которая начинается ровно в момент окончания предыдущей, разрешена.
- Отменённая запись освобождает место.

## Как устроено

```
cmd/shifts           запуск: настройки, подключение к базе, миграции, HTTP-сервер, остановка по SIGTERM
internal/api         HTTP-слой: разбор запросов, преобразование доменных ошибок в статусы
internal/shifts      бизнес-правила и модель; не знает ни про HTTP, ни про PostgreSQL
internal/postgres    реализация хранилища и миграции (встроены в бинарник через embed)
internal/config      настройки из переменных окружения
```

Зависимости направлены внутрь: `api` и `postgres` знают про `shifts`, но не наоборот. Поэтому бизнес-логика тестируется без базы данных (с заглушкой хранилища и управляемыми «часами»), а HTTP-слой — без бизнес-логики.

Настройки (переменные окружения): `DATABASE_URL` (обязательна), `HTTP_ADDR` (по умолчанию `:8080`), `LOG_LEVEL` (`debug`, `info`, `warn`, `error`).

## Ключевые решения

**Нет перепродажи мест.** Запись выполняется в транзакции: сначала `SELECT ... FOR UPDATE` блокирует строку слота, затем считаются занятые места и создаётся запись. Конкурирующие запросы на один слот выстраиваются в очередь, а запросы на разные слоты друг другу не мешают. Тест запускает 25 курьеров одновременно на слот с тремя местами и проверяет, что записались ровно трое. Я проверил и обратное: если убрать блокировку, тест падает (записывалось до 11 человек).

**Пересечения смен запрещает сама база.** Это не проверка в коде приложения, а ограничение в таблице: `EXCLUDE USING gist (courier_id WITH =, period WITH &&) WHERE (status IN ('booked', 'started'))`. Приложение лишь превращает нарушение (код `23P01`) в понятную ошибку, так что даже при ошибке в коде или параллельных запросах курьер не окажется на двух сменах сразу.

**Смена статуса без гонок.** `cancel`, `start` и `finish` выполняются одним `UPDATE ... WHERE status = '<ожидаемый>'`. Если восемь запросов одновременно пытаются начать одну смену, сработает ровно один, остальные получат `invalid_state` (тоже есть в тестах).

**Деньги — целые числа.** Ставка и заработок хранятся в копейках, время считается в секундах: результат не зависит от погрешностей `float`.

**Время можно подменить.** Сервис получает «часы» как зависимость, поэтому правила про окно старта, отмену и заработок проверяются тестами без `sleep` и привязки к реальному времени.

**Эксплуатационные мелочи.** Миграции применяются при старте под advisory-блокировкой (несколько экземпляров стартуют по очереди); сервис ждёт готовности базы; корректная остановка по `SIGTERM` (текущие запросы завершаются); тело запроса ограничено по размеру и не принимает неизвестные поля; паника в обработчике не роняет процесс; логи в JSON через `log/slog`; образ собирается в два этапа и запускается не от root.

## Тесты

```bash
make test               # быстрые тесты; интеграционные пропускаются без базы
make test-integration   # полный прогон на PostgreSQL из docker compose
```

Или вручную: `TEST_DATABASE_URL="postgres://user:pass@localhost:5432/shifts_test?sslmode=disable" go test -race ./...` (отдельная база: перед каждым тестом таблицы очищаются, а для расширения `btree_gist` нужны права на его создание).

Что покрыто:
- правила бизнес-логики и расчёт заработка (таблицы случаев, граничные значения);
- HTTP-слой: коды ответов, некорректный ввод, отсутствие утечки внутренних ошибок, восстановление после паники;
- интеграционные тесты с реальной PostgreSQL: гонка за места, пересечения смен, жизненный цикл смены, фильтры списка, повторное применение миграций.

CI (GitHub Actions) на каждый push проверяет форматирование, `go vet`, тесты с детектором гонок на PostgreSQL, а затем собирает образ, поднимает сервис через Compose и прогоняет `scripts/smoke.sh`.

## Что не сделано

Это учебный проект, и он намеренно ограничен:
- нет аутентификации и разграничения прав (курьера передаёт клиент);
- нет Prometheus-метрик, трассировки и нагрузочных тестов;
- нет кэша и отдельного сервиса расчёта заработка;
- нет идемпотентности повторных запросов записи.

Следующие шаги: метрики и дашборд, кэширование списка слотов, вынос расчёта заработка в отдельный gRPC-сервис.
